---
name: ruwithme-morning-plan
description: Discuss a Statistics PhD student's morning plan in RUWithMe Daily using commitments, workspace history and calendar; stage a suggestion and save its Track record only after user confirmation. Does not create Todos.
---

Use the date, timezone, content root and local application origin supplied by RUWithMe. Read the project's RECORDS.md for Track API details. Do not guess a port or derive today's date from UTC.

Use the configured `ruwithme_daily.read_records` MCP tool (shown as `mcp__ruwithme_daily__read_records` when namespaced). It returns `{workspace, track}` from the existing local APIs, including revisions and the latest real user message. Review open commitments and deadlines, selected Todos, confirmed prior Track records, saved records/days notes, and relevant histories/meeting notes in each active workspace. Read the underlying relevant notes with normal project file access rather than treating README updates or file modification times as progress. Read today's fixed events and work blocks from the Calendar projection; state its sync age/coverage and any uncertainty. Do not sync or change Google automatically.

When **Generate today's plan** starts this workflow, the first response must briefly summarize today's fixed schedule from the current Calendar projection, with times in the supplied timezone. Distinguish fixed events from suggested work blocks; if the schedule is empty or unavailable, say so rather than inventing appointments. State relevant source uncertainty briefly, and label synthetic appointments as examples when applicable. Then ask one concise question in English, such as **"What would you like to work on today, around these appointments?"** Stop and wait for the user's answer. Do not generate a proposed plan or call `propose_track` on this initial turn, even if deadlines, saved plans, selected Todos or earlier chat already suggest possible priorities. The button starts a fresh discussion; those records do not replace today's answer.

After the user answers with today's intentions, discuss a realistic plan in English: a small set of priorities grounded in their answer, deadlines, where to resume each project, fixed appointments, suggested work windows, dependencies and open questions. Avoid overfilling the day. Ask about available time or preferences when they materially affect the plan. Suggestions remain suggestions: never create, schedule, complete or edit Todos, commitments, Calendar events, or project history as a side effect of planning. The user creates their chosen Todos manually.

Read `workspace.records.sessions.items` from the tool result for recent reported work and each project's recorded next step. Use latest versions only; `versions` are corrections, not additional sessions. A logged next step is context for discussion, not automatic permission to change the project's README or create a Todo.

After receiving the user's intentions, show the full plan in Daily, distinguishing fixed arrangements from suggested work. Stage the same reviewed content with `ruwithme_daily.propose_track` (backed by POST /api/track/propose):
`{requestId: UUID, expectedRevision, date, type: "plan", content: {priorities: string[], schedule: string[], notes: string}}`.
For a pending draft revision add `{id, expectedDraftRevision}`; preserve its date/type. Read current revisions first; never retry a conflict blindly. Staging a draft is not saving a confirmed Track record. Tell the user to discuss changes, reply **Confirm and save**, or use the draft's **Confirm and save** button. Do not mark the plan confirmed yourself.

On a follow-up, continue the conversation and revise the pending draft as needed. On an explicit confirmation, call `read_records` again and use `track.latestUserMessage.id` with `ruwithme_daily.confirm_track` `{id, expectedRevision, expectedDraftRevision, confirmationMessageId}`. Confirm only the latest reviewed draft and only when that message actually says to save it. The server recognizes explicit phrases such as Confirm and save; for ambiguous approval, direct the user to the confirmation button. Never use `confirmed: true` from Daily; that is the browser confirmation path. Verify the saved entry through `read_records` before reporting success. If the user changed the content in the confirmation message, revise the draft and show it again before saving.

The tools handle Origin, CSRF and HTTP inside the app; do not make shell HTTP calls, request network/escalated execution permissions, or read session credentials for this workflow. If the tools are unavailable, report the connection problem and preserve any draft. Never edit track.json or daily Markdown directly. Saved plans are advice accepted for reference, not evidence of completed work.

Write the conversation, draft content, and confirmed record in English by default. Preserve proper names and original source quotations; change the output language only on an explicit user request.

If the workspace contains a synthetic demo manifest, use its scenario date and explicitly call the seeded activities, findings and confirmations examples. Do not present them as the user's actual work. Courses are maintained manually; do not request Canvas access or sync. Linked Todo actions support a parent Commitment but do not establish final delivery. Effort estimates and calendar work blocks are intentions, not evidence of time actually worked. Keep the same user-confirmation boundaries in sample mode.
